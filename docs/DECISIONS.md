# 주요 의사결정 기록

CLI 프로토타입을 웹서비스로 확장하면서 정해야 했던 항목들과, 그렇게 정한 이유.

## 1. GitHub — 레포는 사용자가 직접 생성

Agent가 사용자 대신 브라우저 로그인을 할 수 없어서, 레포 생성/권한 설정은
사용자가 github.com에서 직접 하고, 코드 push만 로컬 git 자격증명으로
진행하는 방식을 선택했습니다. (대안이었던 PAT 토큰 발급 방식보다 설정
단계가 적음.)

## 2. Supabase — 프로젝트는 사용자가 직접 생성 후 키 전달

Supabase 프로젝트 생성도 마찬가지로 브라우저 인증이 필요해 Agent가 대신할
수 없습니다. 사용자가 대시보드에서 프로젝트를 만들고 Project URL / anon key
/ service_role key 세 가지를 전달하면, 그 값으로 스키마 마이그레이션과
앱 연결을 진행합니다.

## 3. "DB 데이터 복구"는 샌드박스 mock 데이터로 한정

**결정**: 이 프로젝트가 직접 만든 `mts_orders`/`recovery_snapshots` 테이블
안에서만 "장애 발생 전 상태로 롤백"을 시뮬레이션합니다. 실제 파괴적 명령
(예: 프로덕션 DB의 트랜잭션 롤백, 백업 리스토어)은 구현하지 않았습니다.

**이유**: 실제 운영 DB를 복구하는 기능은 잘못 만들면 되돌릴 수 없는
사고로 이어집니다. 신입사원 과제 데모의 목적은 "이런 흐름으로 자동화할
수 있다"는 개념 증명이지, 실제 파괴적 권한을 가진 도구를 만드는 것이
아니라고 판단했습니다.

**확장한다면**: 실제 도입 시에는 (a) 복구 실행 전 사람의 승인 단계,
(b) 모든 복구 작업의 감사 로그, (c) 되돌리기 어려운 작업에 대한 별도
권한 체계가 반드시 필요합니다. `docs/ARCHITECTURE.md`의 "왜 이 안전장치가
중요한가" 절 참고.

## 4. 장애 원인 설명 — Claude API로 자연어화 (선택적 의존성)

**결정**: 규칙 기반 분석(TF-IDF 유사도 + 정규식 시그니처 추출)은 그대로
핵심 로직으로 유지하고, 그 결과를 사람이 읽기 좋은 문장으로 다듬는 역할만
Claude API에 맡겼습니다. `ANTHROPIC_API_KEY`가 없으면 이 단계만 건너뛰고
나머지는 동일하게 동작합니다 (`src/lib/claude.ts`).

**이유**: 장애 판단(무엇이 얼마나 유사한가, 심각도가 무엇인가)까지 LLM에
맡기면 발표 중 재현이 어려운 비결정적 답변이 나올 수 있습니다. 판단은
결정적인 규칙 기반 로직이 하고, LLM은 "설명을 더 잘 쓰는" 보조 역할로
한정해 안정성과 설명력을 동시에 확보했습니다.

## 5. 배포 위치 — 로컬 개발 경로를 OneDrive 밖으로 이동

**결정**: 최초에는 `~/OneDrive/.../samsung_it/incident_agent`에서 작업을
시작했지만, `npm install`이 OneDrive 실시간 동기화와 충돌해 네이티브
모듈 설치 중 반복적으로 크래시(EPERM, segfault)가 발생했습니다. 프로젝트를
`~/projects/incident_agent`(OneDrive 밖)로 옮긴 뒤 정상적으로 설치·빌드
되었습니다.

**이유**: OneDrive/Dropbox 같은 실시간 동기화 폴더에 `node_modules`를
두면 파일 잠금 문제로 설치가 불안정해지는 것은 Node.js 생태계에서 흔히
보고되는 문제입니다. 나중에 로컬에서 직접 `npm install`/`npm run dev`를
실행할 때도 같은 문제를 겪을 수 있어, 이 경로를 그대로 정본 위치로
유지하는 것을 권장합니다.

## 6. 담당자 알림 — 실제 발송 대신 완전 시뮬레이션

**결정**: SMS/이메일 발송은 실제 발송사(Twilio, Resend 등) 연동 없이
`notifications` 테이블에 발송 로그만 남기고, UI에 "시뮬레이션 · 실제
발송 아님" 배지를 항상 붙입니다 (`src/lib/agent/notify.ts`).

**이유**: 실제 발송에는 유료 계정, API 키, 실제 수신 연락처가 필요하고
발표/데모 환경에서 잘못 트리거되면 실제 사람에게 메시지가 나갈 위험이
있습니다. 이 프로젝트의 다른 "파괴적" 기능(복구, 롤백)도 전부 샌드박스로
한정한 것과 같은 원칙(3번 항목)을 알림에도 동일하게 적용했습니다.

## 7. 장애-시스템 매핑을 `incident_events.source_system`에 비정규화

**결정**: 로그의 `source_system`을 장애 감지 시점에 `incident_events`에도
그대로 복사해 저장합니다 (`tick.ts`).

**이유**: 시스템 구조도(토폴로지 다이어그램)와 발생 시스템 필터가 항상
"열려있는 장애 목록"을 시스템별로 빠르게 나눠야 하는데, 클라이언트가
가진 로그 버퍼는 개수 제한이 있어 오래된 장애의 원본 로그가 이미
사라졌을 수 있습니다. 조인에 의존하지 않고 바로 필터링할 수 있도록
비정규화를 선택했습니다.

## 8. 장애 종료 메타데이터를 `draft_report` 재사용 대신 전용 컬럼으로 분리

**결정**: 기존에 있던 미사용 `draft_report` 컬럼을 재활용하지 않고,
`resolved_at`/`resolution_method`/`resolution_note` 컬럼을 새로 추가했습니다.

**이유**: `draft_report`는 향후 "자동 생성 장애 보고서" 기능을 위해
비워둔 필드로 보였고, 종료 시각/방식/메모는 의미가 다른 정형 데이터라
섞으면 나중에 두 기능이 충돌합니다. 마이그레이션 한 줄 더 늘리는 비용이
필드 의미를 흐리는 비용보다 작다고 판단했습니다.

## 9. "권장 조치 자동 실행"은 새 백엔드 엔드포인트 대신 클라이언트 오케스트레이션

**결정**: 체크리스트 → 검증 → 복구를 한 번에 실행하는 자동화는 새로운
서버 엔드포인트를 만들지 않고, 브라우저에서 기존
`checklist`/`verify`/`recover` API를 순서대로 호출하는 방식으로
구현했습니다 (`IncidentDetail.tsx`의 `runAutoExecute`).

**이유**: 각 단계가 끝날 때마다 진행 상황을 실시간으로 화면에 보여줘야
하는데, 단일 서버 엔드포인트는 중간 진행률을 스트리밍하기 번거롭습니다.
기존 API의 동작(권한, 상태 전이 규칙)을 그대로 재사용할 수 있다는 점도
새 엔드포인트를 만들 이유를 줄였습니다. 대신 탭을 닫으면 자동 실행이
중간에 끊긴다는 한계가 있으며, 데모 목적상 감내할 수 있는 트레이드오프로
봤습니다.
